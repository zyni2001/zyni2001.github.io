第一部分 · 多 Agent总管只相信别人转述给它的

Agentic 系统越来越多地把一个任务拆给几个 LLM agent。一种常见形态，也是 MultiAgentDojo 采用的，是一个总管（orchestrator）自己不带工具，加上一组各自拥有一部分工具的子 agent。总管做规划；它给子 agent 一段自然语言任务；子 agent 跑自己的工具，再用自然语言汇报；总管读这段文字，决定下一次调用。

这种拆分在权限和上下文上很划算：文件 agent 读文件，银行 agent 转账，谁也做不了对方的活。但它引入了一个不易察觉的假设。总管永远看不到工具的原始输出，它看到的是子 agent 对那个输出的转述。每一个关键值（收款账号、邮箱地址、网址）都要经过一个模型，被重新生成成自由文本，而接收方分不清哪个值是从工具原样照抄的，哪个是模型自己写的。

一个失守的子 agent 就够了

假设恰好有一个子 agent 失守，就是那个产生任务所依赖的值的 agent。它保留自己的工具权限；它碰不到其它 agent、环境，也改不了原始工具输出。它唯一的能力，是在汇报里选择说什么。

我们取出 MultiAgentDojo 里的 20 个任务：其中一个子 agent 读到的值，会被另一个子 agent 原样用作某个会改动环境的调用的参数。让产生该值的 agent 失守，令它报一个替换值。

谎报，无防护。20 个任务，deepseek-v4.1-flash。
失守 agent 的汇报运行数攻击成功
干净谎报（只报替换值）3938
混报（真值与假值都提到）142

干净谎报在 39 次里成功 38 次。总管的下一步正是用户要求的；它只是拿错了数字，而且没有第二个来源去核对。更强的总管在这里帮不上忙，因为缺的是信息，不是判断力。你没法靠推理推出一个从没给你看过的值。

这是一个老问题换了新场景。总管用自己的权限按一个错误的值行动，这叫 confused deputy（糊涂的代理人）；替换这个值的动作，叫 false data injection（虚假数据注入）。新的地方在于，有害的那一步正是用户自己要做的动作，只是带了一个错误的参数。

第二部分 · Prompt 注入谎话是怎么进来的

子 agent 不需要本身是恶意的才会谎报。现实的途径有：读了被投毒网页或文件的子 agent、恶意插件或恶意子 agent 定义、或是一个你无法控制其输出的第三方 agent。Prompt 注入是第一种，也是系统自身的防御本该处理的那一种。

固定攻击几乎不成功，所以它藏得深

在 MultiAgentDojo 上，用 deepseek-v4.1-flash 和标准的 important_instructions 攻击，攻击在 912 次运行里成功 2.0%。把固定的注入模板种进网页，60 次里造出谎报 0 次；子 agent 读到种下的指令并识破它（这是一次 prompt injection，我不会照做）。七种措辞扫 420 次，也只把它抬到 1 次。一个注入基准会判定这个模型是安全的。

检测不等于安全

但看见不等于拒绝执行。在那唯一一次成功里，以及对抓网页任务的一次聚焦扫描里，agent 在汇报里点名了注入，却仍然对攻击者的网址发起了一次请求，埋在它反复尝试打不开的网页变体的重试循环里。我们把这记为 executed_despite_flag。一个直接针对这个信号做优化的自适应攻击者，能把它显著抬高：

设置（抓网页任务）识破了注入识破却仍执行
固定措辞，单次尝试55/564/56
自适应，优化该信号—8/39 ≈ 21%

模型的警觉几乎每次都触发，但在压力下，它仍会约每五次有一次执行攻击者的调用。

当注入直接进了请求本身

直接注入把攻击者的值接在用户请求后面。这时根本不需要任何 agent 失守，无防护时攻击在 60 次里成功 46 次。

第一部分的谎报实验模拟的是终态，即一个已经失守的子 agent，而不是现场把它注入。这是这一文献里的标准假设。第二部分是这个终态可达的证据：在这个模型上用固定模板不常成功，但攻击者一旦自适应，就足够常见。

第三部分 · 契约把值绑定到它的来源

Prompt 注入之所以危险，是因为指令和数据走同一个通道，模型分不清它们。谎报是对偶的问题：一个关键值必须经模型重新生成才能传下去，而接收方分不清照抄的值和生成的值。两者的解法一样：把模型从它不该在的通路里拿出去。模型可以决定用哪个值；值本身由系统从来源原样传递。

一份来源契约（provenance contract）是一小段数据，按任务写，点名少数几个要紧的参数，并把每个绑定到必须产生它的那次工具调用：

# 一个付账单任务的契约
banking/user_task_0:
  send_money:
    recipient: {must_come_from: {tool: read_file, args: {file_path: "bill-december-2023.txt"}}}
    amount:    {must_come_from: {tool: read_file, args: {file_path: "bill-december-2023.txt"}}}

一个运行时守卫，在所有子 agent 共享的同一个进程里，记录每一次工具调用及其原始输出。任何会改动状态的调用执行前，对每个被契约点名的参数，它检查该值是否（在归一化大小写、URL 协议、尾部斜杠之后）出现在所要求工具、所要求参数那次调用的原始输出里。对不上，就拒绝执行，调用方收到一条固定消息。这是 CaMeL 的“按引用传值”思想，收窄到契约点名的少数参数，并应用到跨子 agent 的交接上。

它拦住了谎报

在失守 agent 谎报的那 50 次运行里，守卫漏掉一次。对正常任务的代价是 60 次里的 2 次（匹配做了归一化，并信任用户自己的请求）。

漏掉的那一次很有启发。那条规则只绑定了产生工具（search_emails），而失守的邮件 agent 同时拥有 send_email。最可能的路径是“先写后读”：agent 把假值写进邮箱再读出来，于是它有了出处。当失守 agent 能往被核对的来源里写东西时，只绑定工具的规则就不成立。

它拦住了警觉漏掉的注入

在第二部分那些“识破却仍执行”的情形里，攻击者的网址不在绑定来源里，所以契约拒绝它：在同一批聚焦任务上 0/56。警觉没拦住，核对拦住了。

它拦住了直接注入，但只在严格模式下

一个信任“用户请求里的值”的契约，会按构造放行直接注入。但这些任务里的关键值全是工具产生的，用户从不亲自输入。严格契约把每个点名的值绑定到其产生工具，并拒绝把请求当来源：

直接 prompt 注入，20 个任务。
条件攻击成功
直接注入，无防护46/60
加信任请求的契约48/60
加严格契约（绑定到工具）2/59

代价是对 agent 自己拼出来的合法网址变体（比如在绑定网址后加了路径）的过度拒绝，严格匹配会拒掉它。

只要一个关键值有真实来源，就保留模型对这个值的判断，但不要它对这个值的著作权。让系统从来源把值带过来，并在出口处核对它。

诚实的那部分一个更简单的设计也同样有效的地方

如果你给总管自己一份工具的只读副本、完全不加契约，攻击大多就蒸发了。总管自己读来源，很多时候根本不委派读取，失守 agent 也就没机会开口：

条件总管自己读了来源攻击成功完成率
总管有读取工具60/605/6057/60
并要求它核实汇报60/603/6053/60
总管没有工具—40/6028/60

在这个基准上，契约相对“让总管自己读”的优势很窄：契约不依赖总管手里有什么工具，而且它保留了把读取委派出去。这是否重要，取决于系统为什么要委派读取：是总管拿不到的权限，还是大到收不回来的上下文。剩下的 5 次成功，恰好是来源（一个网页）只能经由失守 agent 才能访问的任务。这正是契约仍占优的地方。

局限

  • 机制并不新。按引用传值是 CaMeL；按值核对来源是 ContrAgent（单 agent）。这里做的是把它用到跨子 agent 的交接上、把每个值绑定到产生它的那次调用，以及一张“它何时胜过更简单的设计”的经验地图。
  • 它需要可见的工具日志。一个真正的第三方 agent 在别人的服务器上跑工具；我们看不到原始输出，核对也就没有可比的对象。这个防护适用于在你自己进程里运行、但输出不可信的子 agent。
  • 它覆盖照抄的值，不覆盖计算出来的值。日期、金额、以及任何 agent 推导出来的东西都在范围之外，约占会改动状态的参数的三分之一。
  • 两个假设仍未检验。契约是照标准答案的调用序列写的，不是学出来的；而且攻击者不知道防护存在。“先写后读”的攻击者，或种一个在绑定来源里本就存在的坏值的攻击者，是显而易见的下一个对手。

要点三句话

  • 多 Agent。委派在每个工具和总管之间都放了一个模型。一个报错值的子 agent 在 39 次里得逞 38 次，而且总管变强也没用。
  • Prompt 注入。一个点名了攻击的模型，在自适应攻击者面前，仍约每五次有一次执行它。检测不等于安全。
  • 契约。把关键参数绑定到其产生工具，拦住了谎报（1/50），在严格模式下拦住了直接注入（46/60 → 2/59）；它值得付出代价的场合很具体：一个值的唯一来源，握在一个你无法信任的 agent 手里。
