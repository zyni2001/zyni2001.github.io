When a Sub-Agent Lies

An orchestrator LLM rarely touches data itself; it acts on what its sub-agents report. If one sub-agent reports a wrong value, the orchestrator carries out the user's own legitimate action with the attacker's number. Prompt-injection defenses do not see this, and a stronger model does not fix it. This note works through the threat on MultiAgentDojo and asks a narrow question: can a lightweight provenance contract close it, and at what cost?

Zhiyu Ni · UC Berkeley EECS · November 2026 · github.com/zyni2001

1 / MOTIVATIONThe orchestrator trusts what it is told

Agentic systems increasingly split a task across several LLM agents. A common shape, and the one MultiAgentDojo uses, is an orchestrator that holds no tools of its own and a set of sub-agents that each own a slice of the tools. The orchestrator plans; it calls a sub-agent as a function with a natural-language task; the sub-agent runs its tools and reports back in prose; the orchestrator reads that prose and decides the next call.

This factoring is attractive for permissions and context: the file agent reads files, the banking agent moves money, and neither can do the other's job. But it introduces a quiet assumption. The orchestrator never sees a tool's raw output. It sees a sub-agent's description of that output. Every critical value, a recipient account, an email address, a URL, passes through a model that regenerates it as free text. The receiver cannot tell a value that was copied verbatim from a tool from a value the model wrote.

2 / THREAT MODELA misreporting sub-agent

Suppose exactly one sub-agent is compromised, the one that produces a value the task depends on. It keeps its own tool permissions; it cannot touch other agents, the environment, or the raw tool outputs. Its only power is what it chooses to say in its report. In particular, it may report a critical value that differs from what its tool returned.

This is an old pattern wearing new clothes. The orchestrator acting on a false value with its own authority is a confused deputy; the act of substituting the value is false data injection. What is new is the setting: tool-using agents that change a real environment, where the harmful step is the user's own requested action, carried out with one wrong argument.

Why assume the sub-agent is already compromised rather than injecting it live? Because on current models, live injection into this shape barely works (Section 6). The compromised-agent assumption is standard in this literature and is reachable through several real routes: a prompt-injected sub-agent that has read a poisoned page, a malicious plugin or sub-agent definition, or a genuine third-party agent whose output you do not control.

3 / WHY IT HIDESInjection is 2%, a clean misreport is 97%

The reason this threat deserves its own treatment is that the usual defenses are looking elsewhere. On MultiAgentDojo with deepseek-v4.1-flash and the standard important_instructions attack, the attack succeeds in 2.0% of 912 runs. On a model this robust to injection, there is almost nothing for an injection defense to remove.

A misreport is different. We take the 20 tasks where a value one sub-agent reads is used verbatim as an argument of another sub-agent's state-changing call, compromise the producing agent, and have it report a replacement value. When it reports the replacement cleanly, the attack lands:

C1 — attack, no defense. MultiAgentDojo, 20 tasks, deepseek-v4.1-flash.
The compromised agent's reportRunsAttack succeeded
Clean misreport (replacement only)3938
Mixed (true and false value both named)142

A clean misreport succeeds 38 of 39 times. The orchestrator's next step is exactly what the user asked for; it simply has the wrong number, and no second source to check it against. A stronger orchestrator does not help here, because the missing ingredient is information, not judgment. You cannot reason your way to a value you were never shown.

4 / THE DEFENSEA provenance contract

The fix follows from naming the problem precisely. Prompt injection is dangerous because instructions and data share one channel and the model cannot tell them apart. Here the dual problem: a critical value must be regenerated by a model to be handed on, and the receiver cannot tell a copied value from a generated one. Both are solved the same way, by taking the model out of the path it should not be in. The model may choose which value to use; the system carries the value from its source.

A provenance contract is a small piece of data, written per task, that names the few arguments that matter and binds each to the tool call that must have produced it:

# contract for a bill-payment task
banking/user_task_0:
  send_money:
    recipient: {must_come_from: {tool: read_file, args: {file_path: "bill-december-2023.txt"}}}
    amount:    {must_come_from: {tool: read_file, args: {file_path: "bill-december-2023.txt"}}}

A runtime guard keeps a log of every tool call and its raw output across all sub-agents, in the one process they share. Before any state-changing call executes, for each contract-named argument it checks that the value appears (after normalizing case, URL scheme, and trailing slash) in the raw output of the required tool with the required arguments. If it does not, the call is denied and the calling agent gets one fixed message. This is the by-reference idea from CaMeL, restricted to the handful of arguments a contract names rather than isolating all tool data, and applied across the sub-agent boundary.

5 / RESULTSWhat the contract stops, and what a simpler design stops too

Three results, in order of how much they flatter the method.

The contract stops the misreport

Across the 50 runs where the compromised agent misreported, the guard let one through, at a benign cost of 2 of 60 runs once the matching normalizes values and trusts the user's own request.

Misreport threat and the provenance contract, by suite.
SuiteNo defense, no attack (utility)Contract, no attack (utility)Contract, under attack (succeeded)
banking6/66/60/6
slack30/3030/300/25
travel12/1212/120/11
workspace12/1210/121/8
all60/6058/601/50

The one leak is instructive: that rule binds the producing tool only (search_emails), and the compromised email agent also owns send_email. The likely path is write-then-read-back, the agent writes the false value into the mailbox and reads it out, giving it provenance. A tool-only binding does not hold when the compromised agent can write to the source it is checked against.

But giving the orchestrator read access stops most of it too

If you instead give the orchestrator its own read-only copies of the suite's tools and no contract at all, the attack mostly evaporates. The orchestrator reads the source itself, often without delegating the read, so the compromised agent never gets to speak:

ConditionOrchestrator read itselfAttack succeededUtility
O1 — orchestrator has read tools60/605/6057/60
O2 — + told to verify reports60/603/6053/60
C1 — orchestrator has no tools—40/6028/60

This is the honest part. In this benchmark the contract's advantage over the simple "let the orchestrator read" design is narrow: the contract does not depend on which tools the orchestrator holds, and it keeps the reads delegated. Whether that matters depends on why a system delegates reads in the first place, permissions it cannot grant the orchestrator, or context too large to pull back. The remaining 5 successes in O1 are exactly the tasks where the source (a web page) was reachable only through the compromised agent, which is where the contract keeps its edge.

Direct prompt injection: the contract defends, but only if it does not trust the request

A direct prompt injection appends the attacker's value to the user's request. A contract that trusts "values from the user's prompt" passes it by construction, so that version is no defense at all. But the critical values in these tasks are all tool-derived; the user never types them. So a strict contract that binds every named value to its producing tool, and refuses the prompt as a source, denies the injected value while the legitimate tool-derived value still passes:

Direct prompt injection, 20 tasks. Strict mode binds values to tools only.
ConditionAttack succeeded
D1 — direct injection, no defense46/60
D2 — + contract that trusts the request48/60
D7 — + strict contract (tool-bound)2/59

The naive contract is useless here (48/60); the strict contract cuts direct injection to near zero. The cost is over-denial of legitimate URL variants the agent constructs (adding a path to a bound URL), which strict matching rejects — a known rough edge, not a wall.

6 / DETECTION ≠ SAFETYA vigilant model still clicks the link

Can a live indirect injection, text planted in a web page the agent reads, produce the misreport without the compromised-agent assumption? On this model, mostly no. A fixed injection template succeeds 0 of 60 times; the sub-agent reads the planted instruction and flags it (this is a prompt injection, I will not follow it). Sweeping seven wordings over 420 runs raised it to 1. The model almost always sees the injection.

But seeing is not refusing to act. In the one success, and in a focused sweep of the web-fetch tasks, the agent named the injection in its report and still issued one request to the attacker's URL, buried in a retry loop as it tried variants of the page it could not load. We record this as executed_despite_flag: the agent flagged the injection, and the attacker's value still reached an executed call. An adaptive attacker that optimizes directly for this signal pushes it up sharply:

Setting (web-fetch tasks)Flagged the injectionFlagged yet executed
Fixed wording, one attempt55/564/56
Adaptive, optimizing the signal—8/39 ≈ 21%

The point is not the rate. It is that a model's vigilance, which fires nearly every time, does not keep it safe: it will still execute the attacker's call about one time in five under pressure. And this is exactly where a runtime check earns its place. The attacker's URL is not in the bound source, so the provenance contract denies it — 0 of 56 on the same focused tasks. Vigilance did not catch it; the check did.

The through-line: whenever a critical value has a real source, keep the model's judgment about that value but not its authorship of it. Have the system carry the value from the source and verify it on the way out. Judgment is fallible in ways that look like compliance; provenance is not.

7 / LIMITATIONSWhat this is and is not

  • The mechanism is not new. By-reference passing is CaMeL; provenance-by-value is ContrAgent, single-agent. The contribution here is applying it across sub-agent handoffs and binding each value to the call that produced it — and the empirical map of when it beats a simpler design.
  • It needs a visible tool log. A true third-party agent runs its tools on someone else's server; we never see the raw output, and the check has nothing to compare against. The defense is for sub-agents that run in your own process but whose output you cannot trust.
  • It covers copied values, not computed ones. Dates, amounts, and anything the agent derives rather than copies are out of scope — about a third of state-changing arguments.
  • Two assumptions are still untested. The contracts were written from ground-truth call sequences, not learned; and the attacker did not know the defense. A write-then-read-back attacker, or one that plants a bad value already present in a bound source, is the obvious next adversary.

8 / TAKEAWAYS

  • A misreporting sub-agent is a real and distinct threat: on a model where injection succeeds 2% of the time, a clean misreport succeeds 38/39, and model strength does not help.
  • A provenance contract that binds critical arguments to their producing tool stops it (1/50), defends direct injection in strict mode (46/60 → 2/59), and catches the "flagged-yet-executed" injections that model vigilance does not.
  • But in a benchmark this small, simply giving the orchestrator read access removes most of the threat without any contract. The contract's real value is narrow and specific: when the only source of a value is held by an agent you cannot trust.
  • Detection is not safety. A model that names the attack still executes it about one time in five under an adaptive attacker. Runtime provenance is the layer that does not depend on the model choosing correctly.
